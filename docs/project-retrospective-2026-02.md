# 오머먹 프로젝트 회고

> **작성일**: 2026-02-16
> **프로젝트 기간**: 2026-01 ~ 2026-02 (약 6주)
> **작성 목적**: 프로젝트의 기술적 성과와 사업성을 종합적으로 정리하고, 실제 피드백 기반으로 다음 행동을 결정하기 위한 회고 문서

---

## 1. 프로젝트 개요

### 1.1 풀고자 한 문제

> **"냉장고에 이것저것 있는데, 뭐 해먹지?"**

한국 자취생/1인가구가 매일 반복하는 이 질문을 AI로 해결하려 했다. 기존 레시피 앱(만개의레시피, 해먹)은 "레시피 먼저 → 재료 확인" 순서인데, 오머먹은 **"재료 먼저 → 레시피 생성"** 역방향 접근을 시도했다.

### 1.2 타겟 사용자

- 한국 1인가구 (804.5만 가구, 전체 36.1%)
- 특히 자취생, 사회초년생, 요리 초보
- 월 식비 ~42만원, 배달비 ~9.7만원/월 지출하는 계층

### 1.3 핵심 가설

1. **재료 기반 역방향 레시피 추천은 기존 앱 대비 가치가 있다**
2. **AI 생성 레시피가 충분한 품질을 제공할 수 있다**
3. **사용자들이 이 서비스에 돈을 내고 쓸 것이다**

## 2. 만든 것 — 기술적 성과

### 2.1 기술 스택

| 영역 | 기술 |
|------|------|
| 프론트엔드 | Next.js 14 (App Router), TypeScript, Tailwind CSS |
| 백엔드 | FastAPI, Python 3.11, SQLAlchemy |
| DB | PostgreSQL (Supabase), SQLite (로컬) |
| AI | Claude Sonnet 4.5 (레시피 생성), Gemini (이미지 생성) |
| 인프라 | EC2 t3.small + Docker Compose + Nginx (백엔드), Vercel (프론트) |
| CI/CD | GitHub Actions (자동배포), Cloudflare DNS |
| 모니터링 | Sentry (에러 트래킹) |

### 2.2 구현한 기능 전체 목록

**핵심 기능:**
- 재료 입력 → AI 레시피 3개 생성 (Claude Sonnet 4.5)
- 재료 퍼지 매칭 — 보유 재료 / 추가 구매 재료 자동 분류
- AI 음식 이미지 생성 (Gemini)
- 통합 장보기 리스트 + 쿠팡/네이버 구매 링크
- 3단계 품질 모드 (번개 ~5초 / 기본 ~20초 / 정밀 ~55초)

**정밀 모드 전용:**
- 영양 정보 (칼로리, 단백질, 탄수화물, 지방)
- 대체 재료 제안
- 보관 팁
- 고품질 이미지 (Gemini 2.5-flash, 음식 유형별 앵글/프롬프트)
- YouTube 참고 영상 자동 연결

**사용자 기능:**
- JWT 기반 인증 (회원가입/로그인)
- 보유 재료 관리 (팬트리) — localStorage 기반
- 검색 기록 (이미지 썸네일 카드)
- 즐겨찾기
- 카카오톡/Web Share API 공유
- 다크 모드 (FOUC 방지)
- 3단계 온보딩 오버레이

**비즈니스 기능:**
- 비로그인 IP 기반 3회/일 제한 (소프트 게이팅)
- 로그인 시 무제한
- Google AdSense 광고
- 쿠팡 파트너스 연동 준비

**UX 세부:**
- 태그 기반 재료 입력 (칩 UI, Enter/콤마/Backspace)
- 쇼핑몰 선택기 (쿠팡/네이버 토글, 브랜드 컬러)
- 모바일 반응형 (420px 기준)
- 로딩 오버레이 (레시피 생성 중 애니메이션)
- 로그인 유도 배너

### 2.3 기술적으로 잘한 점

**1. 풀스택 자동 배포 파이프라인**

`git push` 한 번으로 프론트엔드(Vercel)와 백엔드(EC2 Docker) 모두 자동배포. GitHub Actions 워크플로우 2개가 `back/**`, `front/**` 경로 기반으로 분리 실행.

**2. AI 통합 아키텍처**

LLM(Claude) + 이미지 생성(Gemini) + YouTube API를 하나의 요청에서 병렬 처리. `asyncio.gather()`로 이미지 3개 + 영상 3개를 동시 호출하여 추가 대기 시간 최소화.

**3. 프로바이더 패턴**

`LLM_PROVIDER=mock`, `IMAGE_SEARCH_PROVIDER=mock`으로 API 키 없이 전체 기능 테스트 가능. 개발-프로덕션 환경 전환이 환경변수 하나로 해결.

**4. 정밀 모드 차별화**

단순 레시피 생성을 넘어 영양 정보, 대체 재료, 보관 팁, 참고 영상까지 제공. 음식 유형별 카메라 앵글 매핑으로 이미지 품질 차별화.

### 2.4 기술적으로 아쉬운 점

| 항목 | 내용 |
|------|------|
| 테스트 없음 | pytest/jest 모두 0. 수동 테스트 스크립트 2개뿐 |
| TypeScript strict OFF | `"strict": false`로 타입 안전성 미보장 |
| 보안 이슈 | JWT 시크릿 하드코딩, CORS 설정 오류, IP 스푸핑 취약 |
| Docker 헬스체크 없음 | 배포 후 서비스 정상 여부 확인 불가 |
| 모니터링 부재 | CloudWatch 알람 없음, 구조화 로깅 없음 |

(상세 체크리스트: `docs/improvement-checklist-2026-02.md`)

## 4. 실제 피드백 — 원호님 대화 분석 (2026-02-15)

### 4.1 원호님 프로필

- AI API 기반 서비스 개발 경험 풍부 (2024년 초부터)
- 블로그 자동화 서비스 운영 중 (테스터 20명+, 구독 의향자 13명)
- 프롬프트 엔지니어링에 상당한 시간 투자 (1개 만드는데 10분, 검증까지 포함)
- "들으면 구현 가능/불가능 + 원가가 바로 떠오르는" 수준의 실전 경험

### 4.2 원호님의 핵심 피드백

**피드백 1: "저는 자취할때도 뭐 해먹지 보다 뭘 해먹자 라는 생각밖에 안해서"**

→ 본인은 타겟 유저가 아니지만, 핵심을 짚었다. 대다수 사람이 "뭘 해먹자" 유형이고, "뭐 해먹지" 유형은 소수.

**피드백 2: 구독보다 성능/횟수 차이의 프리미엄**

→ "구독을 하려면 사용자에게 구독 이상의 이득을 주어야 한다"

**피드백 3: 레시피 네이밍 어색함 — "김치오리덮밥"**

→ AI 생성 레시피의 품질/신뢰도 문제를 직접 체감. "오리고기 김치볶음밥이면 오 했을텐데."

**피드백 4: "일단 내놓고 반응보고 고도화"**

→ 가장 중요한 조언. 시장 검증 없이 기능만 추가하고 있었다.

**피드백 5: 커뮤니티 제안**

→ "라면 레시피 자랑 → 투표 → 데이터 수집 → 확장". 일방향(AI→유저)이 아닌 양방향 구조를 만들라는 의미.

**피드백 6: "가볍게 들어올수있고 나갈수있고"**

→ 현재 서비스는 너무 무겁다 (재료 입력 → 2분 대기). 유튜브 검색은 5초.

**피드백 7: "누가들어도 오? 할만한거 찾아보세요"**

→ 이 프로젝트에 그 "오?"가 없다.

### 4.3 지인 피드백

> "그냥 유튜브에 검색할꺼같다. 안쓸꺼같다."

### 4.4 원호님의 제품 vs 오머먹 비교

| | 원호님 (블로그 자동화) | 오머먹 (레시피 추천) |
|---|---|---|
| 타겟 | 블로거/마케터 (B2B성) | 자취생 (B2C) |
| 테스터 | 20명+ | 0명 |
| 구독 의향 확인 | 13명이 "산다" | 확인 안 함 |
| 적정 가격 | 월 20만원 (1일 5회) | 월 4,900원 (추정) |
| 대안 | 트렌드 분석 도구 월 10만원+ | 유튜브 무료 검색 |
| 사용자가 느끼는 고통 | 키워드 분석 + 글 작성 시간 | "뭐 해먹지" (가벼운 불편) |

**핵심 차이: 해결하는 고통의 크기가 다르다.**

- 블로그 자동화: 키워드 분석 → 글 작성 → 검증 = 수시간 → 10분으로 단축. 돈이 걸린 문제.
- 레시피 추천: "뭐 해먹지" = 5초 고민. 유튜브/ChatGPT로 이미 무료 해결 가능.

## 5. 종합 판단 — 세 가지 시선의 교차 검증

### 5.1 AI 심층분석 결론

> "현재 '레시피 생성기'로는 투자 가치 없음. 'AI 식생활 어시스턴트'로 전환하면 투자 가치 있음."

주간 식단 + 영양 트래킹 + 식비 절약 증명 = 구독 가치 생성 가능. 하지만 이건 **사실상 새로운 서비스를 만드는 것**과 같다.

### 5.2 원호님 (경험 있는 실무자) 결론

> "가볍게 내놓고 반응 보고. 이거 하면서 다른 것도 동시에 내세요."

기능 확장보다 빠른 시장 검증. 그리고 하나에 올인하지 말 것.

### 5.3 지인 (일반 사용자) 결론

> "유튜브에 검색할꺼같다. 안쓸꺼같다."

가장 냉정하고, 가장 현실적인 피드백.

### 5.4 세 시선의 공통점

**"현재 형태로는 사업성이 없다."**

이유가 다 같다:
1. 해결하는 문제가 충분히 **아프지 않다** (5초 유튜브 검색으로 해결되는 문제)
2. 돌아올 이유가 **없다** (1회성 도구)
3. 돈을 낼 만큼의 가치가 **안 보인다** (무료 대안이 너무 많음)

## 6. 가설 검증 결과

프로젝트 시작 시 세웠던 세 가지 가설을 검증한다.

### 가설 1: "재료 기반 역방향 레시피 추천은 기존 앱 대비 가치가 있다"

**결과: 부분적으로 맞다. 하지만 가치가 충분히 크지 않다.**

"재료 → 레시피" 역방향은 논리적으로 맞고, 기존 앱에 없는 접근이다. 하지만 사용자 입장에서 이 "역방향"의 가치가 유튜브 검색 대비 압도적이지 않다. "김치 계란 레시피" 유튜브 검색 → 영상 10개 → 선택. 오머먹 → 재료 입력 → 2분 대기 → AI 레시피 3개. **속도와 신뢰도 모두 유튜브가 이긴다.**

### 가설 2: "AI 생성 레시피가 충분한 품질을 제공할 수 있다"

**결과: 기술적으로는 됐지만, 신뢰의 문제가 남았다.**

Claude Sonnet 4.5가 생성하는 레시피는 대체로 괜찮다. 하지만 "김치오리덮밥" 같은 어색한 네이밍이 발생하고, 사용자가 "이거 진짜 맛있어?" 확인할 방법이 없다. 만개의레시피의 수십만 후기 vs AI의 "이게 맞나?" — 신뢰 격차를 메울 장치(평점, 후기, 커뮤니티)가 없다.

### 가설 3: "사용자들이 이 서비스에 돈을 내고 쓸 것이다"

**결과: 틀렸다.**

AI 분석, 경험자 피드백, 일반 사용자 피드백 모두 같은 결론. 현재 형태로는 돈을 낼 이유가 없다. 한국 레시피앱 시장에서 구독 성공 사례 자체가 0건이다.

## 7. 남은 것 — 기술 자산과 경험

이 프로젝트가 "실패"라고 해서 아무것도 남지 않은 건 아니다. 오히려 상당한 자산이 쌓였다.

### 7.1 기술 자산 (다음 프로젝트에 재활용 가능)

| 자산 | 재활용 가치 |
|------|-----------|
| FastAPI + SQLAlchemy + PostgreSQL 백엔드 보일러플레이트 | 모든 웹 프로젝트에 즉시 재사용 |
| Next.js 14 App Router + Tailwind 프론트엔드 | 동일 |
| JWT 인증 시스템 | 동일 |
| Claude API 통합 + 프롬프트 엔지니어링 | AI 기반 서비스에 핵심 |
| Gemini 이미지 생성 파이프라인 | 이미지 생성이 필요한 모든 서비스 |
| YouTube Data API + 자막 추출 | 영상 분석 서비스에 재사용 |
| EC2 + Docker + Nginx + GitHub Actions CI/CD | 모든 서비스 배포에 즉시 재사용 |
| Cloudflare DNS + Let's Encrypt SSL | 동일 |
| Sentry 에러 모니터링 | 동일 |
| Google AdSense + 쿠팡 파트너스 연동 | 광고 기반 서비스에 재사용 |

### 7.2 경험 자산 (개발 능력 성장)

### 7.3 사업적 교훈

1. **만들기 전에 5명에게 먼저 물어봐라** — 테스터 0명인 상태에서 6주 개발은 리스크가 너무 높았다
2. **"내가 필요해서"와 "남도 필요해서"는 다르다** — 본인의 니즈가 시장 니즈와 같다고 가정하면 안 된다
3. **무료 대안이 있으면 유료화가 극도로 어렵다** — 유튜브, ChatGPT가 무료로 비슷한 가치를 주는데 돈을 내야 할 이유가 없다
4. **가벼워야 한다** — 재료 입력 → 2분 대기 → 레시피 확인은 너무 무겁다. 유튜브 검색 5초와 경쟁 불가
5. **기능 추가가 아닌 문제 검증이 먼저다** — 정밀 모드, YouTube 연결 등 기술적으로 훌륭하지만 사용자가 원하는지 확인하지 않았다
6. **"누가 들어도 오? 할만한 것"을 먼저 찾아라** — 기술적 가능성이 아닌 사용자의 관심에서 출발해야 한다

## 8. 다음 행동 옵션

### 옵션 A: 포트폴리오 확정 + 새 프로젝트 (추천)

현재 상태로 배포 유지. README 정비. 포트폴리오/이력서에 활용. 기술 자산은 다음 프로젝트에 재활용. 새 아이디어는 "만들기 전에 5명에게 먼저 확인"하고 시작.

**장점**: 매몰비용 최소화. 빠른 다음 시도 가능.
**단점**: 기존 투자 시간 회수 불가.

### 옵션 B: 최소한의 피봇 후 시장 테스트

"AI 식생활 어시스턴트"로 확장하지 않고, 현재 기능에서 커뮤니티 요소(레시피 평가/후기)만 추가 → 커뮤니티/SNS에 배포 → 실제 DAU/리텐션 데이터 수집 → 데이터 기반 판단.

**장점**: 적은 추가 투자로 시장 검증 가능.
**단점**: 핵심 문제(불충분한 고통)가 해결되지 않으면 시간 낭비.

### 옵션 C: 같은 기술로 다른 문제 해결 (피봇)

AI API + 풀스택 + 배포 파이프라인은 그대로 두고, "더 아픈 문제"를 찾아 적용. 예시:
- 콘텐츠 크리에이터 도구 (B2B, 지불 의향 높음)
- 식품/F&B 업체 메뉴 기획 (B2B)
- 특수 식이 관리 (비건, 알레르기, 당뇨 — 니치 but 충성도 높음)

**장점**: 기술 자산 최대 재활용. 사업성 높은 영역으로 이동.
**단점**: 새 도메인 학습 필요.
